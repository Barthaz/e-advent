# Płatności i identyfikacja zamówień — 18.10.2026

## Identyfikatory

- `orders.id` (UUID) jest wewnętrznym identyfikatorem zamówienia. To samo UUID trafia do `order_items.order_id`, `Stripe PaymentIntent.metadata.orderId`, odpowiedzi API `orderId` oraz kolejki e-maili.
- `orders.order_number` pozostaje niezależnym, kolejnym numerem nadawanym przez MySQL. `orderNumberDisplay` / `orderNumber` w odpowiedzi inicjalizacji płatności to czytelny numer klienta, np. `000123`. Jest też w Stripe jako `metadata.orderNumber`. Nie zmieniono istniejącej numeracji ani UUID. Anulowane zamówienia zachowują numer, więc numeracja opłaconych zamówień może mieć przerwy.
- `stripe_payment_intent_id` identyfikuje płatność i pozostaje unikalny w bazie. `calendar.id` nadal identyfikuje konkretny kalendarz, m.in. w adresie `/kalendarz/:id`. Nie zastępujemy tych identyfikatorów numerem klienta.
- Dawne `orderId` z żądania przeglądarki jest tylko referencją klienta w `metadata.clientOrderId`. Nowy losowy `checkoutToken` służy autoryzowaniu ponowień i zmian zakupu; przechowujemy wyłącznie jego SHA-256 w `checkout_sessions`.

## Zachowanie

API zapisuje zamówienie, pozycje i powiązanie sesji w jednej transakcji przed kontaktem ze Stripe. Tworzenie PaymentIntent używa klucza idempotencji `order:<UUID>`. Sekret płatności jest wydawany dopiero po zapisaniu powiązania PI → zamówienie. MySQL `GET_LOCK` serializuje żądania tej samej sesji i zakupy tych samych kalendarzy między instancjami API. Wszystkie operacje pod blokadą korzystają z jednego połączenia z pulą.

Ponowienie z tymi samymi danymi zwraca tę samą płatność. Zmiana klienta, adresu lub pozycji wymaga potwierdzonego anulowania poprzedniego PI, a następnie tworzy nowe zamówienie; poprzedni zapis zostaje w historii. Płatności `processing`, `succeeded` i `requires_capture` blokują taką zmianę. API nie zastępuje zaginionego PI innym bez sprawdzenia. Przy niepowiązanym PI i zamówieniu starszym niż 23 h wymaga uzgodnienia przez operatora, ponieważ Stripe nie gwarantuje zachowania klucza idempotencji bezterminowo.

Webhook sprawdza podpis na surowym body, UUID/referencję legacy, klienta, skrót danych zamówienia, kwotę pobraną, walutę i pozycje. Nowe zamówienia dodatkowo wiążą kalendarz z zapisanym właścicielem i SKU. Aktywacja wszystkich pozycji i zapis zadania e-mail następują w jednej transakcji. Powtórny webhook zachowuje kody dostępu i stan realizacji. Opóźnione zdarzenie błędu nie obniża statusu późniejszej udanej płatności.

Zmiana projektu lub właściciela w kreatorze anuluje jego nieopłaconą płatność przed zapisem danych. Darmowa aktywacja korzysta z tej samej blokady kalendarza. Administrator nie może ręcznie zmienić statusu Stripe ani adresu nieopłaconego zamówienia Stripe. Korekta adresu po opłaceniu pozostaje dostępna w panelu.

Potwierdzenie produktu fizycznego idzie do kupującego. Kod odzyskania kalendarza interaktywnego idzie do właściciela zapisanego w pozycji zamówienia, który może być inną osobą niż płatnik. Błąd e-maila nie cofa opłacenia; webhook zwraca 500, a trwałe zadanie umożliwia ponowienie przez webhook i cron. Blokada zadania zapobiega równoczesnej wysyłce przez dwa procesy, a log wysłanych wiadomości pozwala pominąć już wysłane części zamówienia. SMTP nie zapewnia dokładnie jednokrotnej dostawy: awaria po przyjęciu wiadomości przez SMTP, ale przed zapisem logu może skutkować duplikatem wiadomości, nigdy nowym kodem lub innym zamówieniem.

Strona sukcesu korzysta wyłącznie z pozycji i adresu zamówienia autoryzowanego sekretem konkretnego PI. Ignoruje obce `calendar_id` w URL i stare podsumowania z pamięci przeglądarki. Pokazuje wszystkie zakupione linki, także w zamówieniu mieszanym. Oczekiwanie na webhook nie jest przedstawiane jako odmowa płatności. Nowy koszyk nie jest czyszczony po powrocie ze starszej płatności. Formularz Stripe jest ukrywany natychmiast po zmianie adresu/danych i montowany ponownie z właściwym sekretem.

## Wdrożenie — jeszcze niewykonane

1. Na kopii bazy/testowym środowisku uruchomić `npm run migrate:checkout -w e-advent-api -- --test`. Skrypt wymaga jawnych `MYSQL_TEST_HOST`, `MYSQL_TEST_DATABASE`, `MYSQL_TEST_USER`, `MYSQL_TEST_PASSWORD`; nie używa produkcyjnych wartości zastępczych. Tworzy tylko `checkout_sessions` i `order_email_jobs`, bez przepisywania zamówień i numeracji. Wymaga wcześniejszego schematu `orders`, `order_items`, VAT, numerów zamówień i logów e-mail.
2. Zweryfikować pełny zakup w Stripe TEST z webhookiem `/api/v1/stripe/webhook`, właściwymi kluczami TEST i kontrolowaną skrzynką SMTP. Sprawdzić fizyczny koszyk, kalendarz interaktywny, powrót z przekierowania, odrzucenie płatności, dwie karty, zmianę adresu, powtórzenie webhooka i awarię SMTP. Porównać UUID i numer we wszystkich miejscach, a także odbiorcę i link w e-mailu.
3. Dla produkcji wykonać kopię bazy i uruchomić tę samą migrację z `--prod` z jawnymi `MYSQL_HOST`, `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`. Wdrożyć API i frontend razem. Stare otwarte strony bez `checkoutToken` otrzymają prośbę o odświeżenie. Stare otwarte zamówienia kalendarzy nie są automatycznie przejmowane przez nową sesję; wymagają dokończenia istniejącej płatności lub świadomego anulowania. Trwające stare webhooki są obsługiwane tylko przy zgodności zapisanego `metadata.clientOrderId` i klienta.
4. Ustawić harmonogram wywołujący `POST /api/v1/cron/order-emails` co 5 minut z nagłówkiem `Authorization: Bearer <CRON_SECRET>`. Endpoint obsługuje też GET. Istniejący dzienny cron wykonuje dodatkowe ponowienie awaryjne. Endpoint przetwarza do 20 zadań na wywołanie; monitorować zaległości i `last_error` w `order_email_jobs` oraz błędy webhooka w Stripe. Częstotliwość wymaga konfiguracji harmonogramu hostingu; nie zmieniono planu Vercel.

Nie wykonywano migracji na prawdziwej bazie, rzeczywistych obciążeń karty, wysyłek SMTP ani wdrożenia. Automatyczne testy używają atrap Stripe/MySQL/SMTP; test HTTP podpisu używa rzeczywistej funkcji weryfikacji Stripe SDK na lokalnie podpisanym payloadzie. Blokady i transakcje wymagają jeszcze testu integracyjnego na docelowym MySQL — test jednostkowy nie zastępuje takiego sprawdzenia.

Dokumentacja kontraktu Stripe: [idempotencja](https://docs.stripe.com/api/idempotent_requests), [anulowanie PaymentIntent](https://docs.stripe.com/api/payment_intents/cancel), [webhooki](https://docs.stripe.com/webhooks).
